# YouIyouX web

The design language hub: find an element, see its contract, tokens and rules, preview the real component, and see exactly where it lives in each project. Local-only for now: no accounts. Everything reads a static snapshot except Rules, Style (saving) and Changes, which talk to the local workflow service that `youiyoux ui --project` starts.

```sh
pnpm install        # at the repository root (apps/* is in the workspace)
cd apps/web
pnpm dev            # http://localhost:5173, on the demo system
```

Or, from anywhere, with the CLI:

```sh
youiyoux ui                                              # the demo system
youiyoux ui --design ~/src/acme-design                   # your design repo
youiyoux ui --project ~/src/acme-app                     # plus where it is used in a product (read-only scan)
youiyoux ui --project ~/src/acme-app --config ~/src/acme-design/acme-app.youi.json   # config kept outside the product
youiyoux ui --project ~/src/acme-design/pilot/acme-app --root ~/src/acme-app            # the same, from the config's directory
youiyoux ui --config ~/src/acme-design/pilot/acme-app/youi.project.json --root ~/src/acme-app   # the usage map, without the rule editor
youiyoux ui --detect .youi/detect/detect.json            # plus a youiyoux detect report on Library > Stack
```

The hub shows one design system at a time, read from a snapshot directory. The committed default (`snapshot/`) is the made-up demo system, so `pnpm dev` works on its own and the tool repo holds no product's data. `youiyoux ui` with a system named writes its snapshot to `.hub/` (gitignored) and starts the dev server on that instead, so pointing the hub at a real system never changes the checkout.

Rules and Changes are live rather than a snapshot when the rule editor runs: `youiyoux ui --project <dir>` starts it beside the dev server, which proxies `/api` to it.

### From npm

`npx youiyoux ui` has no Vite: the npm package carries this hub built (`vite build` on the committed demo snapshot, its data left out) and `scripts/hub-server.ts`, its own server, which serves it with a snapshot's `public/` and everything the dev server adds: Try it, `/__youi/query`, Discover's previews and thumbnails, fetching every registry's listings (`/__youi/discover-every`), `/api` proxied to the workflow service, and with `--watch` an event stream (`/__youi/events`, named in `index.html`) on which each new generation is announced, as the dev server's HMR event does. It answers on 127.0.0.1 only and refuses any other `Host`. A named system's snapshot goes to a temporary directory, removed when the hub stops (Ctrl-C included).

The preview frame is built without Vite (`scripts/frame.ts`): the package carries a kit (`/kit/`): the frame's own code, and React, Radix (dialog, label, separator, slot, switch, tabs), cva, clsx, tailwind-merge and lucide-react as one module each, sharing one React, with Tailwind's sheets and Geist. For each snapshot the server bundles every `<name>.demo.tsx` with esbuild, those packages left to the kit, the snapshot's own component files the only others it may import (a demo that imports anything else is listed in `demos.js` with why, and the frame says so in its place), and compiles the frame's sheet with Tailwind's compiler, the system's `system.css` and every class name in the frame's code and the system's components (`/frame/`).

## Data

`pnpm data [--design <dir>] [--project <dir>] [--config <file>] [--root <dir>] [--inventory <file>] [--detect <detect.json>] [--out <dir>] [--commit <sha>]` (`scripts/snapshot.ts`) builds a snapshot with this repository's `@youiyoux/core`, `@youiyoux/tokens` and `@youiyoux/scanner`; it never runs code from the design repo. With no options it rebuilds the committed demo: `examples/demo-design`, a scan of `examples/demo-app`, and an inventory of the scanner's two inventory fixtures (`packages/scanner/test/fixtures/inventory/{console,site}`).

- `--design` is the design repo checkout (the directory holding `youi.config.json`). `--project` (or `--config` with `--root`) scans a product repo, read-only, for the usage map; its `youi.project.json` (or `--config`) also names the design repo, the system, the CSS variable prefix and the Tailwind names its components use. The snapshot records the commit that last changed the definitions it read.
- `<snapshot>/public/data/`: `manifest.json` plus content-hashed `<system>.catalog.<hash>.json` (tokens resolved per scheme, component contracts and their owned files, rules, the design narrative) and `<project>.usage.<hash>.json` (validated against `youi.usage/v1`). The browser keeps hashed files in Cache Storage, so repeat visits and offline work need only the manifest. Vite serves them beside `public/` and copies them into the build.
- `<snapshot>/public/data/<project>.screen.<hash>.webp`: the project's screens, light and dark, when it has captured them (see [Project screens](#project-screens)). The manifest lists them per route; a route without a picture shows an empty state.
- `<snapshot>/public/data/inventory.<hash>.json`: a `youiyoux inventory` file (`--inventory`, validated against `youi.inventory/v1`; a bad file is refused with the failing field), split so the Inventory page's first paint does not grow with the library: this small index (named by the manifest's `inventory`), `inventory.<project>.<role>.<hash>.json` chunks (looks, their families and specimens; a Storybook story's look carries its `story`, and the index's counts are of real looks only), only those of the roles and projects the filters show: a role's as its row nears the screen, the rest one at a time when the browser is idle, and `inventory.extras.<hash>.json` (kits, primitives, flags), all listed in the manifest's `inventoryFiles`. `youiyoux ui --inventory <file>` passes it through. A snapshot older than the split, naming a whole inventory file, still opens.
- `<snapshot>/try.json`: for Try it, each inventoried project's root (relative to the snapshot) and tsconfig, and each component specimen's recipe with its sibling looks (same file, role and wrapper chain, in line order, at most six). Beside `public/`, never in it, so it is never copied into a build, and the dev server's `server.fs.deny` names it (`tryIndexDeny`), so no route serves it (`/snapshot/try.json`, `/.hub/try.json`, `/@fs/…`, `?import`, `?raw`), to the hub or to a page on another localhost port; the dev and preview servers' `/__youi/try?project=<id>&specimen=<id>` reads it and accepts ids only (anything else is a 404).
- `<snapshot>/public/data/discover.<hash>.json`: Discover's listings for a static host (no `/__youi/query`): the default sources' `index.json` from the Discover cache (`--discover <dir>`, else the CLI's cache when it has been synced; never in the committed demo), slimmed to what a card shows and is searched by, at most 2,000, official first; named by the manifest's `discover`. Listings only: no source.
- `<snapshot>/public/data/specimens.<project>.<light|dark>.<hash>.css`: each inventoried project's real CSS for its specimens, with forced-state twins for the state strips, and in its chunks static HTML per look. Built here, never by `youiyoux inventory`, by `packages/scanner/src/specimens`: the stylesheets its pages load, in page order (sheets its server or source code reads and inlines first, ahead of the Tailwind output: string paths in `readFileSync`/`readFile`/`fs.promises` calls, `new URL('./x.css', import.meta.url)`, `?raw`/`?inline` CSS imports; then `<link rel="stylesheet">`s in `index.html`, other HTML and server templates, a link to a Tailwind CLI output mapped to the entry its `package.json` script builds; then what its layouts and components import; then any Tailwind entry nothing links, imports or reads, only when the page loads no other Tailwind entry (else it is skipped, and the output says so); or exactly the list in its `youi.project.json` `specimens.css`, or in the `specimens.css` of a `--config` kept outside the product, for the product its `root` or `--root` names, so the product is never edited), each Tailwind v4 entry compiled with the project's own installed `@tailwindcss/node` and oxide scanner in a worker with a time limit, `/fonts/…` files inlined as data URIs, `prefers-color-scheme` fixed per scheme; component looks server-rendered with esbuild and the project's own React from its node_modules (so CVA classes and Radix `data-state` come out as the app makes them), anything else, or a component that does not bundle, throws or overruns its time limit, as its tag and classes; an icon-size component (`size="icon"`, `icon-sm`, …) with no text of its own gets an icon, not a placeholder word. The snapshot's notes say which sheets were used and how, and its output lists each project's stylesheets in page order, then any Tailwind entry it skipped. Nothing outside the project root is read or run: a `../` or absolute `@import`, a symlink, font path, recipe file or tsconfig `paths` entry that leads out of it, and a package not in the root's own `node_modules`, are refused with a note. Nothing is written into the project: entries are cached by commit and content under `$XDG_CACHE_HOME/youiyoux/specimens` (`~/.cache/…`; `YOUI_SPECIMEN_CACHE` overrides), and a hit runs neither Tailwind nor esbuild. A project not on this machine, or with no stylesheet a page loads, gets none: its tiles draw the look's measured shape.
- `<snapshot>/public/data/detect.<hash>.json` and `detect.shot.<hash>.png`: a `youiyoux detect` report (`--detect`, validated against `youi.detect/v1`) and its element screenshots, renamed by content and named in the manifest's `detect` entry. Like project screens it belongs to whoever ran it: the committed demo snapshot never holds one (`--detect` needs `--out`).
- `<snapshot>/preview/`: `system.css` (the system's variables scoped to `.system-scope`, the surface it sits on, and its Tailwind theme) and the system's owned component files, which the preview frame renders.
- `src/styles/generated/`: the hub's own tokens (`design/youiyoux.*.json`, DTCG, built by `@youiyoux/tokens` like any system's) as CSS variables and a Tailwind v4 theme. The hub replaces Tailwind's colour, radius, shadow, type and easing scales with its tokens (the reserved names are mapped explicitly in `scripts/snapshot.ts`), so it uses no style that is not a YouIyouX token. Rebuilt with the default snapshot.

## Previews

The element Overview shows a captured image (`<snapshot>/public/previews/<component>.<scheme>.webp`) until someone clicks; then it loads `preview.html`, which renders the system's own demo for that component with the system's tokens, in its own document. Demos live in the design repo, beside each contract: `components/<name>/<name>.demo.tsx`, a default-exported React component that imports the owned files by their vendored names (`./button`, `./utils`). A component with no demo says so in the frame. The style editor uses the same frame with `?screen=components|type|scale|motion|focus` (and `token` for the phone's edited token, sent as `yx-preview-focus`) and posts it the unsaved edits as CSS-variable overrides (`yx-preview-vars`, per scheme) and a pinned state (`yx-preview-state`: the frame copies its `:hover`, `:active`, `:focus-visible` and `:disabled` rules under `[data-pin-state]`); see `src/preview/protocol.ts`. The frame's `system.css` writes aliases as `var()` references, so an override of one token reaches every token that reads it. The frame gets its own Tailwind sheet, so a system's vocabulary (shadcn's `bg-primary`, or the demo's `bg-accent`) never collides with the hub's.

`scripts/capture.sh [base-url] [previews|screens|all]` refreshes the thumbnails (into the running snapshot) and the review screenshots in `screenshots/` (light and dark) with `chrome-devtools-axi`. The committed screenshots show the demo system.

The Inventory page is captured with Playwright instead: `playwright-core` (a pinned dev dependency) driving its headless-shell Chromium, never `chrome-devtools-axi`.

```sh
pnpm exec playwright-core install chromium-headless-shell   # once; the browser is not committed
pnpm dev                                                    # in another terminal
node scripts/capture-inventory.ts [--base http://localhost:5173] [--out screenshots]
node scripts/capture-inventory.ts --serve [--out screenshots]   # or: snapshot the fixtures, build and serve it itself
```

Once every specimen frame on screen has drawn, it writes at 1440×900 `inventory.{light,dark}.png` (filters, headline, top of the wall), `inventory-filtered` (`?type=button&project=console`), `inventory-compare` (a compare card, its slider dragged, then moved by a key so its focus ring shows), `inventory-compare-states` (that card's States), `inventory-fixes`, `inventory-drawer` (a family opened), `inventory-states` (its Variants as States: each look's strip), `inventory-try-tabs` (the console's Tabs after Try it, its second trigger clicked in the live frame), `inventory-lead` (`?project=mobile`), `inventory-stories-wall` (`?type=button&project=storybook`: uses and stories counted apart, and a family only stories have) and `inventory-stories` (that family's Variants: Storybook-labeled story tiles beside the discovered looks), and at 390×844 (mobile, touch) `phone-inventory` (the two-column wall), `phone-inventory-filters` (the filters' sheet), `phone-inventory-compare`, `phone-inventory-compare-states`, `phone-inventory-fixes`, `phone-inventory-sheet` (a family's bottom sheet), `phone-inventory-states`, `phone-inventory-try-tabs`, `phone-inventory-lead`, `phone-inventory-stories-wall` and `phone-inventory-stories`, each `.{light,dark}.png`. With `--serve`, Try it is answered by `vite preview` from the fixtures' snapshot. It also checks, into `inventory-checks.json`, that on a phone every control on the page and in both sheets is at least 44px tall, and that at both widths no lead tile (wall, compare, fix) is blank; it exits 1 when one fails. `--serve` adds the `widgets` fixture, shaped like the Toolroll console (its Tailwind entry built by the CLI and linked from `index.html` and a server template), the `sketch` fixture, which loads no stylesheet, so one tile shows the shape-only fallback, and the `mobile` fixture, whose back button is used most in a look that is `display: none` at the 1280px desk width, so its lead tile draws the desktop look instead of a blank, and the `storybook` fixture, whose CSF 3 stories are read beside its app's buttons and badge.

Discover's gallery pictures come from `youiyoux discover previews [--port n] [--registry @shadcn|all] [--role r] [--limit n] [--force]` (`scripts/capture-discover-thumbs.ts`) against a hub running on your project (`youiyoux ui --project <dir>`): for each registry item it opens `/discover/specimen`, which asks the hub's server for the candidate exactly as opening it does (only its source fetched, run only in the sandboxed frame), photographs both stages at 2x in headless Chromium (any request to another host aborted and counted) and keeps them as WebP in the Discover cache, `thumbs/<project>/<key>.<scheme>.webp` with `index.json` (`scripts/discover-thumbs.ts`). A picture is kept while its listing's provenance digest is unchanged; a candidate that cannot be drawn on its own is recorded with why and not tried again until it changes; `--force` takes them all again. The hub's own `devDependencies` carry the packages official shadcn items draw with when a project lacks them (`radix-ui`, `recharts`, `sonner`, `react-day-picker`, `vaul`, `embla-carousel-react`, `input-otp`, `next-themes`, `react-resizable-panels`); they are only bundled into previews, never into the hub.

The Discover page is captured the same way, from recorded responses only: `node scripts/capture-discover.ts [--out screenshots]` builds a Discover cache from `packages/discover/test/fixtures/http` (the items it opens recorded into the cache's source/), builds the hub against the committed demo snapshot (the console fixture is the project) and serves it with `vite preview`, then writes at 1440×900 and 390×844 `discover-search`, `discover-preview` (shadcn's command in the console's theme) and `discover-compare` (Find alternatives from the console's 32px button, shadcn's button beside it, the slider dragged), `phone-` prefixed on the phone, each `.{light,dark}.png`. It aborts and fails on any request that leaves this machine or any source fetched during the capture, and checks into `discover-checks.json` that on a phone every control on the page and in the candidate's sheet is at least 44px tall.

## Project screens

The Screens pictures belong to the product, like its usage map: they live in `<product>/.youi/screens/` (or any directory passed as `--screens`), never in this repo. `screens.json` there names each route and the address that shows it:

```json
{ "schema": "youiyoux.screens/v1", "project": "acme-app", "source": "acme-app demo, seeded data", "capturedAt": "2026-10-11",
  "viewport": { "width": 1440, "height": 900 }, "screens": [{ "route": "/settings", "path": "/settings" }] }
```

Capture from a running copy in development (`vite`, `next dev`) with seeded or demo data, never someone's working instance. Behind a sign-in, save a signed-in session first (`npx playwright codegen --save-storage=auth.json <url>`) and pass it with `--storage-state`:

```sh
youiyoux screens capture --project ~/src/acme-app --base http://127.0.0.1:3000 [--storage-state auth.json]
youiyoux ui --project ~/src/acme-app        # or: pnpm data --project ~/src/acme-app --out .hub
```

Each route is photographed whole (up to six viewports long), light and dark, and its components are placed: in a React development build every component keeps the stack of the JSX that created it, and the served module's source map turns that into the file and line, written beside the pictures as `<slug>.places.json` (`youiyoux.places/v1`). On the screen's page the System elements are outlined on the picture (lookalikes in the warning colour; **All** names any component under the pointer); pointing names one, clicking picks it out with its file:line, the component that rendered it and a link to its element. The pick is in the address (`?select=<element id>` or `?select=<file:line>`), and an element's Usage tab and Top screens open each screen with it lit. A production build is placed without lines, and says so.

**Requests.** With something picked, **Request** files a change request or a comment on it: on this one, or on every use of its element. It goes through the workflow service (`youiyoux ui --project`, session key required) into the product's `.youi/requests/<id>.json` (`youi.request/v1`), with the route, component, element, file:line and box, so it is reviewed in git and an agent reads it without the hub (`requests_list`, or `youiyoux requests`). Each request is a numbered pin on the picture (accent while open, green once addressed, grey closed) and a thread beside it: replies, and who moved it on. An agent replies and marks a request addressed with what it changed; a person closes it (**Looks right: close**) or reopens it. The open request is in the address too (`?request=<id>`). Filing one keeps the screen as it was beside it (`<id>.before.webp`); once an agent has made the change and captured that route again (`youiyoux screens capture --route <route>`), the thread shows **Before** and **Now**, each cropped to the component (found again on the new picture by its file and line, from the new places), and says so when the picture is no newer than the request, with the capture command to copy.

Issues reach a screen through the scanner's file-to-route map, even when a file renders no system element. A violation, lookalike or unresolved site counts on every route that reaches its file through scanned imports. Files with no known route appear under **Not on any screen**, with a reason. Older snapshots need a new scan to place their issues.

| Project routes config | How files reach screens |
| --- | --- |
| `expo-router` | Route files under `appDir`, their layouts and imported files |
| `map` | Files matched by each map entry and their imported files |
| `shell` | Matching files and their imports belong to the app shell (`*`) |
| `none` | No routes inferred; explicit shell entries still apply |
| Import edges | Static imports, re-exports, literal `import()` (including `lazy`), `require()` and CSS `@import` are followed |
| Route boundaries | Walks stop at other screen or shell files, except when forwarding a default component |
| Finding routes | Violations, lookalikes and unresolved sites look up their file in `fileRoutes`; they do not repeat route lists |

The usage map saves `fileRoutes` for every scanned file. Imports stay within the scan's include/exclude set; type-only imports are left out. Unrouted reasons explain what imports the file and how to place it; global stylesheets can go in `routes.shell`. Focused scans explain that routes were not checked.

## Preview deploys

Every pull request can get its own link to the hub built from that branch, so a change is tested in the browser before it merges. The preview is public (unlisted, `noindex`), so it only ever shows the committed demo snapshot.

```sh
pnpm build:preview   # tsc + vite build on snapshot/, then check dist/
pnpm serve:preview   # serve dist/ on $PORT (default 8080), health at /healthz
```

- `scripts/build-preview.ts` ignores `YOUI_HUB_SNAPSHOT` and fails unless every file under `dist/data` and `dist/previews` is byte-identical to `snapshot/public` and the manifest lists only the `demo` system. A real system's snapshot cannot reach a preview by accident.
- `scripts/serve-preview.ts` is a dependency-free Node server: client routes fall back to `index.html`, hashed assets and data are cached for good, everything else revalidates, and it never serves outside `dist/`.
- `.railway/railway.ts` (Railway Infrastructure as Code) declares one service, `youiyoux-web`, built by Railway's default builder from the repository root with `pnpm --filter @youiyoux/web build:preview` and started with `node apps/web/scripts/serve-preview.ts`.
- `.github/workflows/web-preview.yml` runs the same preview build on every PR, with no secrets. Railway's own bot comments each PR's preview link when its environment is ready.

### Turning it on

None of this touches an outside account until someone with access to the Railway workspace and the `ap9000/youiyoux` repository does these steps:

1. In Railway, create a project (or pick one) and install the Railway GitHub App on `ap9000/youiyoux`. The repository is private, so a project member needs a connected GitHub account with access to it.
2. From the repository root: `railway login`, `railway link` (that project, `production` environment), `railway config plan` to review, then `railway config apply`. This creates the `youiyoux-web` service from `main`.
3. Give that service a Railway-provided domain (Service → Settings → Networking → Generate Domain). PR environments only get domains when the base service has one.
4. Project Settings → Environments → **Enable PR Environments**. Leave Bot PR Environments off unless agent-opened PRs should get previews; PRs opened from accounts outside the workspace are never deployed.
5. Open a PR. Within a few minutes Railway's bot comments with the preview link.

No secrets are needed: the build reads only the repository. Closing or merging a PR deletes its environment.

## Speed

Budgets: search under 50 ms, navigation under 100 ms, initial download (first route, fonts included) under 150 KB. `pnpm build && pnpm measure` writes `perf/report.json` and fails over the budgets in `perf/budget.json`; `pnpm measure:inventory` builds and serves 50- and 5,000-look inventories and fails when the Inventory page's first paint grows with the library (`perf/inventory.json`); `pnpm measure:discover` serves 40- and 5,000-listing Discover caches and fails when Discover's first paint grows, its route is over budget, or anything is fetched or mounted for a candidate nobody opened (`perf/discover.json`); [PERFORMANCE.md](PERFORMANCE.md) has the latest numbers and how they were taken. Home shows live search and navigation timings for the current tab.
